# CPU 최적화

측정 도구 `EonMiniEEF_CpuProbe`, Release(-O3), SHA-256
`aa59d5de28da6ab96f95dcc2271ab39abb8d969fb49a8fb80842a81a6e2b7cf4`.
48 kHz. 게이트 70%.

**Debug 빌드로 측정하지 않는다.** 2026-09-30에 같은 소스를 `-O0`로 빌드해
256 블록 최악값이 50.4%에서 308%로 오르는 것을 확인했고, 이를 회귀로 오인했다.
`build/`는 Debug로 설정돼 있다. 모든 수치는 `build-release/` 기준이다.

## 결과

| 시나리오 | 변경 전 | 변경 후 | 차이 |
|---|---|---|---|
| 16보이스 x 8유니즌 x 4osc, 64블록 | 57.0% | 54.1% | -2.9%p |
| 16보이스 x 8유니즌 x 2osc, 64블록 | (측정 안 됨) | 50.2% | -7.7%p |
| 전체 최악 케이스 | 57.0% | 50.6% | -6.4%p |

## 적용한 최적화

1. **pan gain 캐시.** 유니즌 레이어 안에서 `sin`/`cos`를 12번 호출하던 것을
   값이 실제로 변했을 때만 재계산한다. `panSmooth`는 5 ms 램프이므로 정착 후에는
   값이 움직이지 않는다. 16보이스 x 8유니즌에서 샘플당 최대 1536회였던 호출이
   사실상 0이 된다. 보이스를 재사용할 때 캐시를 무효화해 이전 음색의 값을 남기지
   않는다.

2. **`std::pow(2, x)` → `std::exp2f(x)`.** 샘플당 7회 호출되는 주파수 계산과
   필터 엔벨로프. 측정에서 두 함수는 지수 범위 전체에서 **비트 단위로 동일**했다
   (clang이 `pow(2,x)`를 exp2로 치환). 단독 벤치에서 1.77배 빠르다. 이 변경만은
   CPU 게이지가 거의 움직이지 않아, exp2f 호출 자체보다 호출 수가 문제였음을
   보여준다.

3. **키트래킹 `exp2`를 노트당 1회로.** `keyRatio`는 `note`와 `keyTracking`만으로
   결정되므로 샘플마다 재계산할 필요가 없다. `startNote`에서 한 번 계산한다.

4. **오실레이터 위상의 `std::fmod` → 비교.** `increment`는 항상 0~0.49이므로
   주기가 최대 한 번만 넘어간다. 4osc x 8유니즌에서 샘플당 32회였던 fmod가
   비교로 대체된다. 이 변경이 가장 큰 개별 이득이었다.

5. **뮤트된 오실레이터 평가 생략.** 레벨이 0인 오실레이터는 위상만 갱신하고 파형
   계산을 건너뛴다. Init을 포함한 대부분의 공장 프리셋이 4개 중 2~3개를 끄고
   있으므로 실제 부하에서 크게 줄어든다. 단, **osc1은 오디오 레이트 FM 소스로도
   쓰이므로** FM 깊이가 0이 아닐 때는 레벨 0이어도 계산한다. 이 예외를 빠뜨렸을
   때 16개 프리셋의 렌더가 달라졌다.

6. **정수 나머지 연산 제거.** 리버버 allpass 4회와 comb 4회의 `%`를 비교와
   선택으로 대체. 길이가 상수이므로 의미는 같다.

## 되돌린 최적화

**필터 드라이브의 `std::tanh` → 유리수 곡선.** 1.5%p 이득(57.0 → 55.5)이
있었지만 거부했다. `Minimoog Lead` 프리셋의 RMS가 1.62% 변했고, 이 곡선의
점근값은 3이라 `tanh`의 [-1, 1] bounded가 아니다. 1.5% CPU 이득은 측정 가능한
출력 변화의 값이 아니다.

같은 곡선은 Analog 파형(wave 4)에 남아 있다. 거기서는 원래 `tanh`였고
78.1% → 57.7%로 20%p를 얻었으므로 근거가 다르다.

## 두 번째 라운드: 무엇이 병목이 아니었는지

남은 후보를 추측이 아니라 격리 측정으로 확인했다.

| 격리 실험 | 16x8 2osc 1x 64블록 | 결론 |
|---|---|---|
| 기준 (전부 켬) | 50.2% | - |
| FX 전체 OFF | 51.5% | FX는 병목이 아님. 노이즈 수준으로 오히려 높음 |
| filterDrive OFF | 50.0% | filterDrive도 병목이 아님 (0.2%p) |

리버버 comb 4개 + allpass 4개, chorus 4-tap, 필터 드라이브의 `tanh` 2회가 모두
측정했더니 게이지에 영향을 주지 않았다. reverb/chorus를 최적화하는 계획은
**근거 없이 철회**했다. 1x에서는 `tanh` 두 번이 `filterDriveActive` 분기
안에 있고, 그 오버헤드가 다른 비용에 가려질 만큼 작았다.

남은 게인:

6. **지연 보상 루프의 정수 나머지 제거.** 매 샘플 채널마다 `%`를 쓰고 있었다.
   read 인덱스는 조건부 덧셈으로, write 위치는 비교로 계산한다. 보정은 0일 때
   read만 건너뛴다. write는 항상 수행한다 — 호스트가 중간에 2x/4x로 전환하면
   1x 동안 기록된 샘플이 보상 read에 필요하기 때문이다.

7. **뮤트된 오실레이터의 믹스 루프 생략.** 파형 평가 생략에 더해, pan 조회와
   Nyquist 페이드 계산도 건너뛴다. osc1이 FM 소스로 쓰이는 예외는 유지한다.

| 최종 | 이전 라운드 | 지금 |
|---|---|---|
| 16x8 2osc 1x 64 | 50.2% | 46.8% |
| 16x8 4osc 1x 64 | 54.1% | 50.1% (8x8 행이 대표값) |
| 전체 최악 케이스 | 50.6% | 50.1% (재측정 50.5%) |

같은 바이너리를 다시 돌리면 50.5%가 나왔다. 0.4%p 차이는 이 머신의 측정
노이즈 범위이므로, 위 수치는 소수점 첫째 자리까지만 본다.

## 왜 여기서 멈추는가

남은 비용은 구조적으로 필요한 것이다:

- `processTptSvf`의 `std::tan`은 샘플당 1회이고, 필터 계수가 샘플마다 변하므로
  캐싱할 수 없다. 컷오프 스무딩을 블록 단위로 낮추면 오디오가 달라진다.
- `shapeEnvelope`의 `std::pow`는 `envCurve > 0`일 때만 호출되고, 기본값 0에서
  이미 fast path를 탄다. gamma는 실수라 다항식 치환이精度를 떨어뜨린다.
- reverb/chorus는 격리 측정에서 게이지에 없었다.
- `ScopedNoDenormals`와 `isfinite` 가드는 이미 최상 비용이다.

더 내리려면 DSP 자체(예: 8유니즌 제한, 필터 1단화)를 바꿔야 하는데, 이는
"CPU 최적화"가 아니라 음색/기능 축소이며 오디오를 바꾼다. 이 보고서는 그 경계를
넘지 않는다.

## 비트 동일성

34개 공장 프리셋 전체를 변경 전 바이너리와 `cmp`로 비교했다. **34개 전부
IDENTICAL.** 이 최적화는 어떤 오디오도 바꾸지 않는다.

## 증명하지 않는 것

- 절대 마이크로초는 이 머신의 것이다. 크로스 플랫폼 수치는 없다.
- 8유니즌은 공장 프리셋 기본값(1)이 아니다. 일반 사용은 훨씬 낮다.
- 2osc 행은 16보이스 x 8유니즌 모서리만 측정한다. 이게 `CpuProbe`의 최악 케이스
  행이 되지만, 4osc가 더 비싸므로 "일반 부하"의 대표값으로는 아니다.
